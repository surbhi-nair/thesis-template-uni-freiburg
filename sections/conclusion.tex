\section{Conclusion}\label{sec:conclusion}

In this thesis, we investigated to what extent an LLM agent can automate the semantic modeling of structured data by generating SPARQL CONSTRUCT queries. Our approach converts a dataset into a generic KG \(G_D\) and lets a GRASP generation agent remodel it, testing every query on \(G_D\), with an independent review agent checking the result. We compared it with the general-purpose coding agent OpenCode on eight datasets with 3 to 239 tables.

\paragraph{RQ1:}
For schemas of up to 47 tables, the agent produces good semantic models. All thirteen GRASP query sets executed on QLever without changes, and the judge scores of all GRASP runs on these datasets range from 7.5 to 9.2 out of 10, with at most two major issues per run.

\paragraph{RQ2:}
Without competency questions, our approach scores at least as high as the baseline on all seven datasets where both produced a result, and higher on six. On the BIRD databases, the mean is 8.5 against 7.6, with 3 major issues against 16, and the gains lie in relationships, entity modeling, vocabulary, and self description. Six of the twelve baseline query sets did not run on QLever, although the baseline reported them as tested. On IMDb, the GRASP graph is also simpler and faster to query on every analytical question. On Mondial, the two graphs trade shortcuts, and neither is better on all questions.

\paragraph{RQ3:}
Competency questions raise the baseline mean from 7.6 to 8.1, mainly through better coverage and typing, but lower the GRASP mean from 8.5 to 8.3, because the agent narrows its model towards the questions. They help an agent that otherwise misses data, and can harm one that already explores it thoroughly.

\paragraph{RQ4:}
The score does not follow the number of tables: Mondial (47 tables) scores 8.9, card\_games (6 tables) lowest among the BIRD databases. Datasets are hard when their domain is far from their schema. Only MusicBrainz, with 239 tables, drops to 6.7. The characteristic failure modes are:
\begin{itemize}[leftmargin=*, itemsep=1pt]
  \item relationship predicates that are reused for different meanings or point in the wrong direction;
  \item parts of a large schema that are never read;
  \item datatypes that force casts or silently drop values, such as \texttt{xsd:gYear} years and dates built as strings;
  \item predicates shared across entity types, and merged roles that remove distinctions a user needs.
\end{itemize}
These errors produce well-formed triples and become visible only when the output is queried.

\paragraph{Limitations:}
Each configuration was run and judged once, and the judge is the same LLM as the generators, DeepSeek~V4.1~Flash, which is the only model we used. The agents only see samples of the data. The analytical questions were written by us, and the held-out competency questions have not yet been used to measure answerability.

\paragraph{Future work:}
\begin{itemize}[leftmargin=*, itemsep=1pt]
  \item \textbf{Review on the output.} Letting the reviewer query the materialized output, for example with the competency questions, would expose wrong directions and dropped values that the queries do not show.
  \item \textbf{Questions as tests.} Giving competency questions only to the reviewer could keep their benefit without narrowing the model.
  \item \textbf{Large schemas.} Modeling large schemas in parts, with a consistency check across parts.
  \item \textbf{Broader evaluation.} Repeated runs, further LLMs, and answerability on the held-out questions.
\end{itemize}

Overall, an LLM agent that explores and tests against the data produces good semantic models for schemas of up to a few dozen tables, and better ones than a general-purpose agent. Since its output is a set of CONSTRUCT queries, a human expert can find and correct the errors that remain.
